Open with the one-line promise: a chatbot that runs in the browser and knows your page — no backend, no bill, no data leaving the device.

The four pills are the spine of the whole talk: local-first, site-aware RAG, pluggable, offline. Don't dwell — move straight to the problem.

02 · THE PROBLEM

Site chatbots make you pick a pain.

⊗ Generic

Pre-built bots know nothing about your content. Ask "what's your refund policy?" on a docs site and you get "I don't have information on that." Useless.

$ Leaky & costly

API-powered bots send every visitor question to a third-party server. You pay per token, babysit an API key, and your visitors' questions leave the page.

The result Small sites are stuck — too small to build a backend chatbot, too privacy-conscious to ship questions to a cloud API. So they ship nothing.

Two failure modes, both real and common. Generic bots are useless; API bots leak data and meter every call.

The punchline is the callout: small sites end up with nothing. That gap is exactly what Local Whisper fills.

05 · WHY IN THE BROWSER?

Why not just run a model on a $5 server?

"Local" can mean a server you run, or the browser itself. For a site owner with a static page, the browser wins on every axis that matters.

  • Static hosts can't run backends. GitHub Pages, Netlify, a CDN portfolio — no server process exists. A chat server means leaving static hosting behind.
  • Infra is real work. Provision, scale, keep a box alive, secure and patch it. That's a side-project of its own.
  • The visitor's device is free compute. Modern phones and laptops run a small LLM fine — why pay for a server when the user already has a CPU?
  • Privacy scales for free. "Your data never leaves your device" is automatically true when there's no server for it to leave to.
The shift Move the work from your server (which costs you money and sees user data) to the visitor's device (which is free and already trusted with the data). The site owner ships a script tag, not a server.

Pre-empt the obvious objection: "why not a cheap server?" Four reasons — static hosts can't, infra is real work, the visitor's CPU is free, and privacy is automatic.

The mental shift in the callout is the takeaway: move compute to the device. The site owner ships a script tag, not a server.

06 · ARCHITECTURE

Two contexts, one postMessage bridge.

The widget is a sandboxed iframe — it can't read a cross-origin parent page directly. So a tiny script (embed.js) runs in the host page instead, where it's always same-origin to itself, scrapes the content, and hands it over.

🌐 Your page (host)

  • embed.js runs here — same-origin to itself
  • Scrapes visible content into sections
  • Scrolls to the section on link click
sections→postMessage
scroll-to←link click

🤖 Chat widget (iframe)

  • React app + Wllama (WebAssembly)

This split is why it works on any site: the scraper lives where the page is readable, the model lives where it can run sandboxed. Neither privilege is violated.

The cleverest part of the design. An iframe cannot read a cross-origin parent — browser security forbids it. So embed.js runs in the host page instead, where it's same-origin to itself and can always scrape.

Content crosses to the iframe via postMessage (which works cross-origin). Neither side breaks its security model. That's the whole trick.

07 · HOW THE CHAT WORKS

A real LLM, loaded as WebAssembly.

  • GGUF model → Wllama → WebAssembly. The model file is compiled to WASM and runs on the visitor's CPU. No server round-trip per message.
  • Tiny by design. Default is Gemma 3 270M (~278MB); presets run 270M → 1B — small enough to download once and keep.
  • Cached = offline. After the first load the model is in the browser cache; the widget works with no network.
  • You can swap it. Upload a different .gguf (up to 2GB) — bigger model, smarter answers, more RAM.
# the whole inference path, no server: model.gguf → Wllama (WASM) → visitor's CPU → answer in the widget

Demystify "AI in the browser": it's a real LLM, compiled to WebAssembly, running on the visitor's CPU. No server round-trip per message.

Default is Gemma 3 270M (~278MB); the preset lineup runs 270M → 1B (Gemma, Llama 3.2, Qwen3, SmolLM2). Bigger = smarter but more RAM. Next slide explains the engine itself.

08 · THE ENGINE — WHY WLLAMA

Why Wllama — and how it actually runs.

  • It's llama.cpp, compiled to WebAssembly. Wllama wraps the same ggml / llama.cpp core that runs Llama-class models natively — real inference, not a toy demo.
  • No GPU, no server. Runs on the visitor's CPU, inside their tab. The browser is the runtime.
  • Multi-threaded, off the main thread. A Web Worker + SharedArrayBuffer use several cores — inference doesn't freeze the page.
  • Streams both ways. Model chunks stream in; tokens stream out. The first answer starts before the whole model is cached.
  • GGUF-native. Loads standard Hugging Face GGUF files — swap models by swapping a file, no recompile.
// how a model reaches the user GGUF model file ↓ llama.cpp / ggml (C++ core) ↓ Emscripten → WebAssembly module ↓ runs in a Web Worker visitor CPU (multi-threaded) ↓ streamed answer in the widget
Wllama is the bridge that makes "a real LLM in a browser tab" practical — the same inference code people run on servers, retargeted to WASM.

Why this engine, not a from-scratch one: Wllama is llama.cpp (the ggml core) compiled to WebAssembly — i.e. the same battle-tested inference code that runs Llama-class models on servers and laptops, just retargeted to the browser.

Two details worth saying aloud: it runs in a Web Worker with SharedArrayBuffer so it uses multiple cores without freezing the UI, and it streams — model chunks in, tokens out. (That multi-core WASM is exactly what needs the COEP/COOP headers from the boundaries slide.) Next slide is the optional deep dive on how this compares to Ollama and friends.

Optional deep-dive slide — skip for a short talk. The landscape of "run an LLM locally" splits cleanly on one question: does it need installing?

In-browser engines (Wllama, WebLLM, transformers.js) need no install → can embed in any site. Native runtimes (Ollama, LM Studio) are faster and run bigger models (real CPU/GPU) but require an app + a running localhost server on each machine — fine for your laptop or a desktop app, impossible for a public website's visitors.

Wllama over WebLLM here: GGUF/llama.cpp ecosystem (matches Hugging Face model availability), mature multi-threaded WASM. WebLLM's edge is WebGPU acceleration where browsers support it. Ollama's architecture: llama.cpp wrapped as a native app exposing a REST API on localhost:11434 — your code calls it like a local OpenAI.

10 · THE GAP

A general model doesn't know your content.

Ask "what's your refund policy?" and a generic model will happily invent one. It's smart about language, not about your site. So you have to teach it — and there are two ways.

Option A · Train

Bake your content into the model's weights (fine-tuning). The model memorizes your site.

Option B · Retrieve

Hand the model the right snippet at question time (RAG). The model reads your site on demand.

Next two slides: why Option A doesn't work in a browser, and why Option B is the whole point of this project.

Set up the RAG motivation. A general model is fluent but ignorant of your content — ask a policy question and it hallucinates a plausible-sounding wrong answer.

Frame the two ways to fix that: train (memorize) vs retrieve (read on demand). The next slide disposes of training for the browser case.

11 · WHY NOT TRAIN A MODEL?

Teaching a model your content by training doesn't fit the browser.

  • Training is heavy. Fine-tuning needs GPU clusters and hours-to-days — not a visitor's laptop on a Tuesday.
  • It's per-site. You'd retrain for every site, and again for every content update. A blog-post edit would mean a retrain.
  • Browsers are RAM/CPU bounded. Even running a tiny model is near the ceiling; training one is off the table.
  • It breaks the promise. Real training wants your data centralized — exactly the server + data-leaving-device setup Local Whisper exists to avoid.
  • The models are tiny by design. A 270M model can't absorb deep site knowledge through weights without forgetting how to talk.
The reframe We don't need the model to remember your site — we need it to read your site on demand. That's a different (and far cheaper) problem.

Deep dive: the project's custom-training R&D notes — why RAG + persona already cover what training would, with zero training.

Knock out Option A methodically. Training needs GPUs + hours, must repeat per-site and per-update, hits the browser's RAM ceiling, and — critically — wants data centralized, which breaks the no-backend promise.

Land the reframe: we don't need the model to remember the site, we need it to read the site on demand. And if someone genuinely wants their "brand voice," the answer isn't training — it's the shipped persona config (next slides). The linked R&D doc makes the full case.

14 · THE TECHNIQUES, NAMED

Six techniques do the heavy lifting.

Each is a deliberate choice. Named here so you recognize them anywhere else you meet them — and can tell they're standard building blocks, not magic.

① WebAssembly inference

The LLM core (llama.cpp) compiled to WASM, runs on the CPU. No install, no GPU, no plugin.

② Sandboxed iframe + postMessage

The widget is isolated; the host script bridges content cross-origin. The security boundary that makes "any site" work.

③ Vector embeddings + retrieval

Text → vectors (bge-small); find the nearest chunks by similarity. How "relevant" is measured.

④ IndexedDB vector cache

Embeddings persist across visits; repeat questions skip the work entirely.

⑤ COEP / COOP isolation

Cross-origin headers that unlock SharedArrayBuffer (multi-threaded WASM). The one fiddly requirement.

⑥ Lazy loading

The ~35MB embedder loads on the first grounded question, not on page load. Fast first paint.

This is the "underline the techniques" slide — name each building block so the audience can google it later and sees there's no magic.

Call out #5 especially: COEP/COOP is the one requirement that can be fiddly on some static hosts, because multi-threaded WASM (SharedArrayBuffer) demands cross-origin isolation. It's also why a "server backend" isn't secretly hiding in there.

15 · PLUGGABLE CHATBOT

Bring your own scraper — or use the built-in one.

  • Default scraper reads visible text grouped under each heading — covers most sites, zero config.
  • Override with getSections for a CMS, a JSON-LD block, an API, or a specific content region.
  • Custom voice or brand? Set PRIVATE_CHAT_CONFIG.persona — one config line, no training.
  • Runs in your page's context — so it can fetch your own APIs and await async data.
  • Degrades gracefully — throw or return empty, the widget falls back to plain chat. No crash.
// your page, before the embed script window.PRIVATE_CHAT_CONFIG = { persona: "Friendly, concise, calls me Acme", getSections: async (doc) => [ { anchor: "pricing", title: "Pricing", text: "…the section text…" } ] };

"Pluggable" means: the default scraper works out of the box, but a site owner can swap in their own via getSections — for a CMS, JSON-LD, an API, or a specific content region.

And the answer to "I want my brand voice" is not training — it's the shipped persona config, one line. Reassure too: the scraper runs in their page context, and if it fails the widget degrades to plain chat, never crashes.

16 · BEYOND ONE PAGE

One widget, the whole site.

  • Static cross-page index. Drop a site-index.json next to your page (built by the bundled crawler — Node, or Python via Scrapling) and the widget answers across pages, not just the current one.
  • SPA-aware. On client-side navigation (React / Vue routers) it re-scrapes automatically — no stale content after a route change.
  • Links go to the right place. A hit on another page links there with an anchor, then scrolls the visitor to the exact section.
Default: just the current page. Add a site-index.json only when you want cross-page answers — everything else works with zero configuration.

One widget can cover the whole site, not just one page. Two mechanisms: a static site-index.json (built by the bundled crawler — a Node script, or Python via Scrapling) for cross-page answers, and automatic re-scrape on SPA route changes.

Reassure: the default is still just-the-current-page. Cross-page is opt-in via one JSON file.

17 · THREE RUNNING MODES

Same widget, any deployment.

① Cross-origin embed

Widget on your domain. embed.js scrapes the host and bridges via postMessage. The common case.

② Same-origin embed

Widget served from the same origin (e.g. the portfolio). Iframe-side scrape is the fallback — same effect, simpler path.

③ Standalone

The app at its own URL, no embed. Plain general chat, no RAG — your private, offline ChatGPT-in-a-tab.

All three are exercised by the test suite. The RAG path only activates in the two embed modes — standalone is a general assistant.

Same widget, three deployments. Cross-origin embed is the common case (widget on your domain). Same-origin is a simpler path when the widget shares the origin. Standalone is just the app at its own URL — a private, offline general chat with no RAG.

20 · HONEST BOUNDARIES

What it can't do (yet).

Said out loud so the rest of this deck reads as honest, not salesy.

  • Tiny models hallucinate. 270M params is sharp for its size, but it'll make things up. RAG grounds it; it doesn't guarantee perfection.
  • Retrieval is brute-force. It scans all chunks — very large sites will feel it in latency and memory.
  • Needs COEP / COOP headers. Cross-origin isolation is a WebAssembly requirement; some hosts make this fiddly.
  • First-question latency. The ~35MB embedder loads on the first grounded question (then it's cached).
  • No deep multi-step reasoning. It reads and answers. It doesn't plan long agentic chains or run tools.
  • Browser memory ceiling. A bigger model is smarter — until the tab runs out of RAM. There's a real trade-off curve.
None of these are fatal — they're the honest cost of "100% in the browser, zero backend." The project picks that trade on purpose.

The honesty beat — say the limits out loud so the rest of the deck reads as credible. Pair each limit with the "why": tiny model → hallucination (RAG grounds, doesn't fix); brute-force retrieval → large-site latency; COEP/COOP → the one hosting friction; first-question latency; no deep reasoning; RAM ceiling.

Close with the callout: none fatal — they're the honest cost of "100% in-browser, zero backend," chosen on purpose.
