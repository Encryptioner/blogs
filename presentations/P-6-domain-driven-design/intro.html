Domain-Driven Design

Why your code should speak the language of the business.

Mir Mursalin Ankur
Lead Software Engineer @ Nerddevs Ltd
"Most software doesn't break because of syntax errors — it breaks because teams lose alignment with the business problem they're supposed to solve."
01 · The Example

The Bug: Two Teams, One Word, Two Meanings

Two small services in an online store. Both use a type called Product. Neither team thinks there's a problem.

// InventoryService — "price" is the wholesale cost we pay the supplier
class Product { sku: string; price: number; stockCount: number; }

// OrderService — imports the SAME Product type from a shared "models" folder
function calculateTotal(product: Product, qty: number) {
  return product.price * qty;   // customer is charged supplier COST, not retail price
}
The real-world outcome
Nobody wrote a bug. Both teams used a reasonable field named price. The system still shipped a real one: customers were charged wholesale cost for weeks before anyone noticed margins had collapsed.
02 · The Problem

Systems Don't Fail on Day One — They Fail as They Grow

  • Early systems succeed because one or two people hold the whole mental model in their head.
  • Late-stage systems fail because that model fractures: teams grow, terminology drifts — exactly what caused the bug on the last slide.
  • Features get bolted on without design consideration. Every new requirement piles more special cases onto assumptions that are already stale.
  • This is rarely a tooling problem — it's a modeling problem. That's exactly the moment Domain-Driven Design (DDD) targets.
The core insight
The hardest part of a complex product was never the codebase. It's agreeing on what the business is actually doing.
03 · Foundations

"Domain" Is the Business — Not the Code

Before DDD makes sense, "domain" needs a plain definition. A domain is the real-world subject matter your software exists to serve — independent of any code. Your business domain is the specific one your company operates in. For our running example, that's Online Retail.

  • Core subdomain — what makes the business money or wins the market. Invest here: Order Management, Pricing.
  • Supporting subdomain — necessary, not the differentiator: Inventory, Fulfillment.
  • Generic subdomain — solved problems. Buy, don't build: Payments Gateway, Auth.

How to find them: don't start from database tables — ask domain experts "what does this part of the business actually do?" Each answer is a subdomain, and each subdomain typically becomes its own Bounded Context in code.

src/
├── order-management/   ← Core domain
├── inventory/          ← Supporting domain
├── fulfillment/        ← Supporting domain
├── payments/           ← Generic domain — thin wrapper around a payment SDK
└── auth/               ← Generic domain — thin wrapper around Auth0 / Cognito
04 · The Idea

Model the Business, Not the Database

DDD is an approach to software design that puts the business domain — not the schema, not the framework — at the center of every decision. It requires engineers to collaborate deeply and continuously with domain experts, not just gather requirements once and disappear into tickets.

  • Not a silver bullet. DDD doesn't generate code and won't fix a legacy monolith by itself.
  • What it gives you instead: clarity about what the system should do, and where it's safe to change.
  • Architecture-agnostic. Works for a monolith or microservices — what matters is whether the model reflects real domain rules.

05 · Fix #1

One Word, One Meaning — Everywhere

Ubiquitous language is a shared vocabulary that developers and domain experts use everywhere: meetings, tickets, docs, and code. Applied to the bug from Slide 2, the fix starts with a naming conversation, not a code review comment:

// After a 15-minute glossary conversation with the business:
// "price" the business pays a supplier is a WholesaleCost.
// "price" the customer pays is a RetailPrice. Never the same field.
class Product { sku: string; wholesaleCost: Money; retailPrice: Money; stockCount: number; }

function calculateTotal(product: Product, qty: number) {
  return product.retailPrice.multiply(qty);   // unambiguous
}

Pros: shared meaning, readable code, better decisions. Cons: upfront workshop effort; sloppy naming breaks the whole benefit.

06 · Fix #2

Make the Confusion Structurally Impossible

Renaming one field fixes one bug. It doesn't stop the next team from importing the wrong Product again — there's still one shared type for two meanings. A bounded context gives each meaning its own model.

// inventory-context/Product.ts — not shared
class Product { sku: string; wholesaleCost: Money; stockCount: number; }

// order-context/Product.ts — not shared
class Product { sku: string; retailPrice: Money; }

Pros: prevents a "big ball of mud"; teams evolve independently. Cons: you must design how contexts talk; wrong splits duplicate logic.

07 · Building Blocks

Inside a Context: Identity vs. Attributes

Inside a bounded context, you still need to model the domain correctly. Two kinds of building blocks do that:

  • Entity — defined by identity and lifecycle. A Customer stays the same person even after their address changes. Entities are mutable.
  • Value Object — defined only by its values, often immutable. Money has no identity of its own — two equal amounts are the same value. Value objects are immutable.
// Entity — has an ID that outlives any single attribute
class Customer {
  constructor(public readonly id: string, private address: Address) {}
  relocate(newAddress: Address) { this.address = newAddress; } // same customer, new address
}

// Value Object — immutable, compared by value, no ID
class Money {
  constructor(public readonly amount: number, public readonly currency: string) {}
  multiply(qty: number) { return new Money(this.amount * qty, this.currency); }
}
08 · Wrap-Up

DDD Is a Tool, Not a Default

Reach for DDD when
The domain is complex and keeps evolving (finance, healthcare, logistics, marketplaces); multiple teams share the system; it needs to live and change safely for years.
Skip DDD when
The app is mostly CRUD; you can't get sustained access to domain experts; the project is short-lived or low-impact.

"You don't adopt DDD by adding patterns — you adopt it by removing ambiguity."
